# DOMAIN-CHAT-CONSTITUTION

채팅 도메인 원칙.

> 작성일: 2026-07-26. 이 문서는 원칙을 정의한다. 구현 규칙은 STATUTE에 둔다.

---

## 1. 책임

* 회원 간 **실시간 채팅**을 소유·관리한다. **1:1(DIRECT)과 그룹(GROUP)을 하나의 "방(room) + 참여자(participant)" 모델로 통합**해 다룬다(1:1은 참여자 2명인 특수 케이스).
* 채팅방·참여자·메시지 데이터의 생성·조회를 제공한다: 방 생성/목록/상세, 메시지 전송(실시간)·이력 조회, 참여자 초대·퇴장, 읽음 처리(안 읽은 수).
* **실시간 신호**(메시지 수신, 입력 중 표시, 접속 상태)를 WebSocket(STOMP)으로 전달한다.

---

## 2. 원칙

* **채팅 데이터의 소유·관리는 이 도메인에 있다.** 방·참여자·메시지는 CHAT이 소유한다.
* **회원(작성자·참여자·발신자)은 원시 `Long`으로만 참조한다.** MEMBER 엔티티를 직접 참조하지 않는다(ARCHITECTURE-CONSTITUTION §4).
  * 응답에 필요한 표시정보(닉네임·인증 뱃지)는 **읽기 시점에 MEMBER 서비스로 협력**해 파생한다. 닉네임을 복제(비정규화)해 소유하지 않는다.
* **REST와 WebSocket의 역할을 분리한다.**
  * WebSocket(STOMP) = "지금 일어나는 일" — 실시간 메시지 송수신, 입력 중(typing), 접속 상태(presence).
  * REST = "상태와 이력" — 방 목록·상세, 지난 메시지 이력, 읽음 처리, 참여자 초대·퇴장.
* **1:1 방은 두 회원당 유일하다.** 정렬된 쌍 키(`directKey`)로 정규화하고 DB unique 제약으로 중복을 원천 차단한다. 방 생성은 find-or-create(있으면 재사용). 그룹 방은 중복 방지 대상이 아니다(같은 구성으로 여러 방 허용).
* **그룹 참여자 관리는 평평한 모델이다.** 방장(owner) 권한 계층을 두지 않는다. 활성 참여자는 누구나 다른 회원을 초대할 수 있고, 본인은 언제든 퇴장(leave)할 수 있다.
* **퇴장은 삭제가 아니라 상태다.** 참여자 퇴장은 물리 삭제하지 않고 `leftAt` 마킹(soft leave)한다. 퇴장하면 방 목록·실시간 수신에서 제외되며, 재입장 시 재활성화한다.
* **메시지는 이번 범위에서 append-only다.** 메시지 수정·삭제는 두지 않는다(범위 밖). 이력 보존을 우선한다.
* **인증은 연결 시점에 한 번 한다.** WebSocket 연결(STOMP CONNECT)에서 JWT로 인증하고, 그 신원(Principal=memberId)이 세션 내내 유지된다. 방 구독·전송은 **그 방의 활성 참여자만** 허용한다.
* **목록·이력 조회는 페이징을 기본으로 한다**(DOMAIN-COMMON-CONSTITUTION §5). 방 목록은 오프셋 페이징, 메시지 이력은 커서 기반(최신→과거).

## 3. 인프라 원칙

* **이번 이터레이션의 메시지 브로커는 Spring 내장 Simple Broker(인메모리)다.** 단일 서버 인스턴스에서 채팅 전체를 완성·테스트한다. 메시지 영속화(MySQL)는 브로커와 별개로 항상 수행한다.
* **다중 서버 확장(scale-out)이 필요해지면 Redis(또는 RabbitMQ) 릴레이 브로커로 교체한다.** 이 교체는 WebSocket 브로커 설정 변경으로 국한되며 도메인 로직(영속화·전송)은 바뀌지 않는다. 도메인은 브로커 중립적인 전송 추상(`SimpMessagingTemplate`)만 사용한다.
* **접속 상태(presence)는 인메모리 레지스트리로 관리한다.** 단일 서버 기준으로 "이 서버에 연결된 회원"을 정확히 추적한다. 다중 서버에서의 정확한 presence는 Redis 기반 구현으로 교체할 수 있도록 인터페이스(`PresenceRegistry`) 뒤에 둔다.

---

## 4. 관계

* **MEMBER**: 방 참여자·메시지 발신자는 회원이다. 표시정보(닉네임·인증뱃지)는 MEMBER가 소유하며, 이 도메인은 서비스 계층(`MemberQueryService.findDisplaysByIds`)으로 협력해 조회만 한다. WebSocket 인증도 MEMBER/보안 인프라의 `JwtProvider`를 재사용한다.
* **VERIFIED-PERFORMER**: 참여자·발신자의 인증 뱃지는 `MemberDisplay.verified`(MEMBER가 VERIFIED-PERFORMER와 협력해 채우는 값)를 통해 파생된다. 소유·관리는 VERIFIED-PERFORMER에 남는다.
* **RECRUITMENT**: 현재 연결 없음(독립). 구인 지원자↔작성자 채팅 연계는 실수요 시 확장한다(RECRUITMENT 범위 밖 명시 항목).

---

## 5. 범위 밖 (현재)

* 메시지 수정·삭제 — 이번엔 append-only. 필요 시 soft delete로 확장.
* 파일·이미지·음원 첨부 — 텍스트 전용. 추후 `FileService` 협력으로 확장.
* 메시지 검색 — 이력 조회(커서 페이징)만.
* 알림 푸시(안 읽은 메시지 알림) — 알림 인프라 도입 시.
* 다중 서버 정확 presence·메시지 릴레이 — Redis 도입 시(§3).
* 방장 권한·강제 퇴장(kick)·방 이름 변경 이력 — 평평한 모델 범위 밖.
* RECRUITMENT/PERFORMANCE 등 타 도메인과의 채팅 연계 진입점 — 실수요 시.
* refresh 토큰 로테이션·읽음 커서의 Redis 캐싱 등 — Redis 도입 시 함께 조율(COMMON-STATUTE §4).
