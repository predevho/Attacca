# 관리자 운영 화면 레이아웃 설계

## 목적

ADMIN만 사용하는 공지 관리와 인증 심사 화면을 공개 콘텐츠 화면과 구분한다. 운영자는 업무의 맥락, 현재 상태, 다음 행동을 빠르게 파악해야 하므로, 일반 `PageContainer`의 읽기 중심 규칙과 별도 운영 프레임을 둔다.

## 현재 상태

- `/admin`은 공지 관리와 인증 심사로 이동하는 허브다.
- `/admin/notices`는 공지 등록·수정·삭제와 목록 재시도를 제공한다.
- `/admin/verified-performers`는 직접 지정, 상태별 심사 목록, 승인·거절·철회를 제공한다.
- 세 화면은 각각 최대 폭, 제목, 보조 문구, 작업 버튼의 위치가 달라 운영 흐름이 늘어날수록 일관성을 잃기 쉽다.

## 결정

`FE/components/admin/AdminPageFrame.tsx`를 만든다. 이 컴포넌트는 운영 화면의 최상위 `main`, 넓이, 상단 제목·설명·보조 행동 영역을 제공한다.

- 기본 폭은 `max-w-5xl`로 한다. 공지 목록과 심사 목록에서 제목·상태·작업이 한 줄에 안정적으로 놓일 수 있는 폭이다.
- 집중형 폼은 `narrow` 폭(`max-w-3xl`)을 사용한다. 공지 등록·수정처럼 한 건을 작성하는 흐름에 한정한다.
- 관리 허브는 각 업무를 카드형 대시보드가 아니라 경계가 분명한 업무 목록으로 유지한다. 현재 두 업무의 정보량에는 요약 지표나 별도 위젯이 필요하지 않다.
- 공지 관리의 `공지 등록`, 인증 심사의 `직접지정`은 각 화면의 주요 행동으로 상단에서 인지 가능해야 한다. 목록 내 수정·삭제, 승인·거절·철회는 행 단위 행동으로 남긴다.
- 오류, 로딩, 빈 상태는 각 업무 영역 안에서 현재와 같은 접근성 역할(`alert`, `status`)과 재시도·행동 문구를 유지한다.

## 화면별 구조

### 관리 허브 `/admin`

1. 제목 `관리`와 운영 목적을 표시한다.
2. 공지 관리와 인증 심사를 같은 업무 목록 규칙으로 보여준다.
3. 링크는 업무명, 짧은 설명, 이동 표시만 갖고 접근 가능한 이름은 업무명과 일치한다.

### 공지 관리 `/admin/notices`

1. 운영 헤더에 `공지 관리`, 설명, `공지 등록` 행동을 둔다.
2. 목록은 유형·고정·제목·일정/장소·행 행동 순서를 유지한다.
3. 등록/수정은 같은 운영 프레임의 집중형 변형 안에서 처리하며, 목록으로 돌아가는 행동을 제공한다.

### 인증 심사 `/admin/verified-performers`

1. 운영 헤더에 `인증 연주자 심사`와 심사 목적을 둔다.
2. 직접 지정 폼은 심사 목록보다 앞에 두되, 목록 상태 탭과 충돌하지 않게 별도 영역으로 구분한다.
3. 상태 탭, 심사 카드, 승인·거절·철회 API 계약은 그대로 유지한다.

## 비범위

- BE API, BFF 경로, ADMIN 판별, 리다이렉트, 공지·인증 심사의 도메인 규칙은 변경하지 않는다.
- 운영 지표, 알림 센터, 대량 선택·일괄 처리, 감사 로그는 도입하지 않는다.
- 새 색상 체계, 사이드바, 데이터 시각화, 외부 디자인 라이브러리를 추가하지 않는다.

## 검증

- `AdminPageFrame`의 기본·집중 폭과 제목·행동 슬롯을 렌더링 테스트로 확인한다.
- 기존 관리자 페이지 테스트에서 관리자/비관리자 리다이렉트, 목록 액션, 상태 탭, 오류·로딩·빈 상태를 회귀 검증한다.
- 전체 FE 테스트·타입 검사·lint·production build를 실행한다.
- 로컬 브라우저에서 데스크톱과 모바일 폭으로 관리 허브, 공지 목록/폼, 인증 심사의 작업 버튼과 가로 넘침 여부를 확인한다.
