# Attacca UI 테마·엔터프라이즈 UI 시스템 설계

- 작성일: 2026-09-14
- 상태: 사용자 검토 대기
- 범위: FE 테마 시스템과 공통 UI 기반의 1차 정비
- 접근: B안 — 토큰·공통 컴포넌트 정비 후 화면을 단계적으로 개선

## 1. 목표

Attacca의 현재 화면은 콘텐츠와 운영 기능이 성장했지만, 화면마다 밀도·상태 표현·색 사용이 달라 서비스 전체가 하나의 제품처럼 보이지 않는다. 이번 작업의 목표는 다음과 같다.

1. 다크모드와 라이트모드가 같은 정보 구조와 접근성 기준을 공유한다.
2. 공개 콘텐츠 화면과 어드민 운영 화면의 밀도를 구분한다.
3. 버튼·입력·탭·배지·표·모달·toast·빈 상태·오류 상태를 공통 규칙으로 통일한다.
4. 기존 도메인 기능과 라우팅 계약을 유지하면서 점진적으로 적용한다.

## 2. 테마 모델

### 2.1 사용자 선택

테마 선택지는 `system`, `light`, `dark` 세 가지다.

- 최초 상태는 `system`이다.
- `system`은 `prefers-color-scheme`를 따른다.
- 사용자가 선택한 값은 `localStorage`에 저장한다.
- 초기 렌더에서 테마가 바뀌어 화면이 깜빡이지 않도록 문서 초기화 스크립트 또는 동일한 서버·클라이언트 판정 규칙을 사용한다.
- 토글은 아이콘만으로 의미가 불명확하지 않도록 현재 상태와 선택 메뉴에 접근 가능한 이름을 제공한다.

### 2.2 토큰 원칙

컴포넌트는 원색을 직접 사용하지 않고 semantic token만 사용한다.

- 배경: `paper`, `surface`, `surface-muted`
- 텍스트: `ink`, `ink-muted`, `ink-faint`, `on-brand`
- 선과 포커스: `line`, `focus`
- 상호작용: `brand`, `brand-strong`, `brand-muted`
- 상태: `success`, `warning`, `danger`, `info`
- 콘텐츠 이미지 위 오버레이: `scrim`

라이트는 따뜻한 종이와 잉크 기반으로 유지하고, 다크는 순수 검정 대신 차콜 기반으로 유지한다. 두 테마 모두 본문·보조본문·버튼·오류·포커스의 WCAG AA 대비를 테스트한다.

## 3. 정보 밀도와 화면 성격

### 3.1 공개 화면

홈·공연·공지·공지 상세는 포스터와 제목·일정·출처가 먼저 보이는 editorial 레이아웃을 사용한다. 큰 장식보다 실제 콘텐츠를 첫 viewport의 주인공으로 둔다.

### 3.2 작업 화면

프로필·채팅·폼은 집중형 레이아웃을 사용한다. 입력 오류, 저장 중, 저장 성공, 네트워크 실패를 같은 위치와 색 규칙으로 보여 준다.

### 3.3 운영 콘솔

어드민·IMPORT는 enterprise 운영 화면으로 취급한다.

- 고정 사이드바 또는 상단 도메인 내비게이션
- 상태 필터와 검색을 목록 상단에 고정
- 표 또는 조밀한 리스트의 행 높이·상태 배지 규격화
- 승인·거절처럼 위험한 명령은 확인 모달과 결과 toast를 사용
- 실행 중·실패·부분 성공·빈 목록을 별도 상태로 표시

## 4. 공통 컴포넌트 1차 범위

새 디자인 시스템을 별도 라이브러리로 만들지 않고 현재 컴포넌트 구조 안에 최소 단위로 추가한다.

- `ThemeProvider`와 `ThemeControl`
- `Button`의 variant와 loading/disabled 상태
- `Input`, `Textarea`, `Select`의 label/error/help 규칙
- `Badge`의 상태 variant
- `Tabs`와 필터 그룹
- `Dialog`와 위험 액션 확인
- `Toast` 또는 `StatusMessage`
- `EmptyState`, `ErrorState`, `LoadingState`

각 컴포넌트는 키보드 포커스, `aria-invalid`, `aria-describedby`, reduced motion을 고려한다. 기존 화면은 한 번에 모두 교체하지 않고 새 컴포넌트가 필요한 화면부터 옮긴다.

## 5. 적용 순서

1. CSS 토큰을 명시적 테마 속성으로 재구성하고 테마 선택·초기화를 추가한다.
2. Header에 테마 선택을 추가하고 로그인·공개 홈·어드민에서 동작을 검증한다.
3. 공통 상태·입력·버튼 컴포넌트를 만들고 NOTICE/IMPORT 화면에 적용한다.
4. `/admin/imports`를 기준으로 운영 콘솔의 밀도·필터·상태 표현을 정리한다.
5. 홈·공지 상세·공연 상세를 공개 콘텐츠 화면 기준으로 정리한다.
6. 나머지 화면은 기능 변경 없이 토큰과 공통 상태 컴포넌트부터 단계적으로 교체한다.

## 6. 테스트와 완료 조건

- 테마 선택이 `system/light/dark` 모두에서 유지되고 새로고침 후 복원된다.
- 라이트·다크 모두에서 텍스트, 버튼, 오류, 포커스 대비 테스트가 통과한다.
- 테마 초기화 시 hydration warning과 화면 깜빡임이 없다.
- 키보드만으로 헤더 테마 선택, 폼 오류 확인, 모달 닫기와 위험 액션 취소가 가능하다.
- 기존 Vitest·typecheck·lint·build·Playwright E2E가 통과한다.
- 모바일 375px과 데스크톱에서 텍스트·버튼·표·필터가 겹치지 않는다.
- 기존 API, 인증, BFF, 도메인 상태 계약은 변경하지 않는다.

## 7. 제외 범위

- 백엔드 API·도메인 규칙 변경
- 새로운 디자인 도구나 외부 UI 프레임워크 도입
- 모든 화면의 전면 재디자인
- 사용자별 커스텀 색상·폰트 업로드
- 애니메이션 중심의 마케팅 랜딩 페이지 제작

## 8. 후속 확장 후보

- 어드민 전용 compact density 설정
- 사용자별 알림 센터와 toast 이력
- 고대비 테마
- UI 컴포넌트 시각 회귀 테스트
