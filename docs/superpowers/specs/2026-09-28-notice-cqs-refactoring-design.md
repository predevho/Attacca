# 공지 서비스 CQS 분리 설계

## 목표

`NoticeService`에 함께 있던 조회와 변경 책임을 분리한다. 외부 HTTP 경로, 요청/응답 DTO, 권한 규칙, 데이터 저장 방식은 바꾸지 않는다.

## 선택

- `NoticeQueryService`: 공개·관리자 조회, `readOnly` 트랜잭션, 조회 DTO 변환.
- `NoticeCommandService`: 등록·수정·삭제·커버 이미지 변경, 입력 검증과 파일 수명주기.
- `NoticeResponseAssembler`: 두 서비스가 공유하는 관리자/공개 응답 변환만 담당한다.

## 트레이드오프

- 장점: 읽기와 변경의 의존성이 분리되어 파일 변경 규칙이 조회 코드에 섞이지 않고, 이후 조회 최적화나 캐시 도입의 경계가 명확해진다.
- 비용: 기존 단일 서비스보다 빈과 파일 수가 늘어난다. 이번에는 실제 관심사가 다른 세 책임만 나누고, 저장소나 DTO는 유지해 과분리를 피한다.
- 제외: API 버전 변경, DB 마이그레이션, 파일 저장소 추상화 변경, 프론트엔드 변경.

## 검증 기준

- 기존 공개/관리자 URL과 응답 DTO를 유지한다.
- `EVENT` 일정 검증, 출처 URL 검증, 이미지 교체 중 이전 파일 삭제 순서를 유지한다.
- 공지 서비스·컨트롤러 테스트와 전체 BE 테스트를 통과한다.
