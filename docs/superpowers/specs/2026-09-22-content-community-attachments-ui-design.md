# 밝은 콘텐츠 커뮤니티 UI·게시글 첨부 설계

## 구현 상태 (2026-09-23)

* **적용**: 기본 밝은 테마, 피드 `/feed/new` 독립 작성, JPG/JPEG·PNG·WebP·PDF 임시 업로드, 파일당 10MB·게시글당 5개 제한, 소유자·임시 상태 검증 후 피드/구인글 연결, 24시간 임시 파일 정리, 상세 화면의 첨부 목록 조회를 구현했다.
* **오류와 재시도**: 선택 단계의 형식·용량·개수 오류는 파일 입력 바로 아래에 표시한다. 업로드 실패는 실패한 파일 행에 사유와 `다시 시도`를 표시하며, 이미 성공한 임시 업로드 ID는 재사용해 중복 업로드하지 않는다.
* **의도적으로 미적용**: 이미지 썸네일/갤러리, 첨부 전용 피드 글, 이미 게시된 첨부의 삭제·교체·순서 변경 API는 이번 범위에 포함하지 않는다. 피드 본문은 기존 서버 계약대로 비어 있을 수 없고, 수정 요청의 새 `attachmentIds`는 기존 파일을 삭제하거나 교체하지 않고 추가만 한다.
* **참고 출처와 적용 범위**: [Toss Business UI reference](https://uibowl.io/self-contents/cmmk1jz2s000ni804jza4m3ql)의 넓은 여백, 명확한 탐색, 행동 우선 구성을 참고했다. 브랜드·문구·시각 자산을 복제하지 않고, 밝은 기본 토큰과 독립 작성 진입점에만 적용했다.

## 1. 배경

현재 피드는 목록 상단의 인라인 작성 폼으로 작성·탐색을 함께 처리하고, 구인 작성 화면도 전역 화면 구조와 시각적 맥락이 분리되어 있다. 이 때문에 서비스가 콘텐츠 커뮤니티보다 앱 패널 집합처럼 보이며, 피드·구인 게시글에는 첨부를 올릴 수 있는 사용자 흐름과 도메인 계약이 없다.

이번 변경은 밝은 바탕의 콘텐츠 중심 화면 체계로 전역 UI를 정리하고, 피드·구인글에 이미지와 PDF 첨부를 안전하게 연결한다. 참조한 토스 비즈니스의 넓은 여백, 명확한 탐색, 행동 우선순위는 적용하되, 마케팅 랜딩의 큰 히어로나 장식용 이미지는 사용하지 않는다.

## 1.1 참고 자료

| 자료 | 적용 범위 | 적용하지 않는 범위 |
| --- | --- | --- |
| [토스 비즈니스 UI/UX 레퍼런스](https://uibowl.io/self-contents/cmmk1jz2s000ni804jza4m3ql) | 넓은 여백, 명확한 전역 탐색, 하나의 주된 행동을 우선하는 정보 위계 | 브랜드 자산·문구·구성의 복제, 랜딩 중심 큰 히어로, 장식용 시각 효과 |

앞으로 외부 자료가 설계·계획·트러블슈팅의 선택에 영향을 주면 각 문서에 `참고 자료` 섹션을 둔다. 각 항목은 원본 URL, 실제 적용 범위, 적용하지 않는 범위를 함께 기록한다. 외부 자료가 없으면 그 사실을 명시한다.

## 2. 목표와 비목표

### 목표

- 밝은 배경과 공통 색 토큰을 기준으로 헤더·목록·상세·작성 화면의 위계를 통일한다.
- 피드 작성은 `/feed/new` 독립 페이지로 옮기고, `/feed`는 탐색과 읽기에 집중한다.
- 피드·구인 공고에서 JPG, PNG, WebP, PDF를 최대 5개, 파일당 10MB까지 업로드·조회·수정·삭제한다.
- 파일별 오류와 폼 검증 오류를 입력 위치와 상단 요약에서 동시에 알린다.
- 서버 검증 실패, 네트워크 실패, 권한 실패, 업로드 실패를 구분해 안전한 메시지로 반환한다.

### 비목표

- 동영상 업로드, 이미지 편집, 드래그 순서 변경
- S3 직접 업로드, CDN, 파일 관리 전용 화면
- 기존 게시물의 일괄 첨부 마이그레이션
- 채팅의 실시간 동작·WebSocket 구조 변경

## 3. 전역 UI 원칙

### 3.1 화면 골격

- 헤더는 흰 배경과 얇은 하단 경계선을 사용한다. 좌측 브랜드, 중앙 주요 탐색(홈·피드·공연·구인·채팅), 우측 인증 상태 행동만 둔다.
- 페이지는 `max-width` 기반 본문형 레이아웃으로 구성한다. 목록은 비교·탐색 가능한 넓은 폭, 상세·작성은 읽기 편한 좁은 폭을 사용한다.
- 모든 영역을 카드로 감싸지 않는다. 반복 목록과 편집 도구만 작은 반경·얇은 경계로 구분한다.
- 브랜드 블루는 링크·주요 행동·선택 상태에만 쓴다. 실제 첨부 이미지와 콘텐츠가 시각적 초점이 된다.
- 모바일에서는 탐색을 메뉴로 접고, 작성·제출 행동은 화면 너비와 터치 영역을 보장한다.

### 3.2 페이지 흐름

| 영역 | 변경 |
| --- | --- |
| 피드 목록 `/feed` | 인라인 작성 폼을 제거하고 페이지 제목, 최신 게시물, `글쓰기` 행동과 목록을 제공한다. |
| 피드 작성 `/feed/new` | 내용, 첨부, 제출·취소를 독립 편집 흐름으로 제공한다. 성공 시 새 글 상세로 이동한다. |
| 피드 상세 `/feed/{id}` | 본문 아래에 이미지 갤러리 또는 PDF 목록을 표시한다. 목록에는 첫 이미지와 `+N`만 표시한다. |
| 구인 목록 `/recruitments` | 기존 상태·악기 필터는 보존하고, 공고 등록 행동과 모집 상태를 우선 배치한다. |
| 구인 작성·수정 | 피드와 같은 입력 폭·오류 패턴·첨부 영역을 사용하되 제목, 모집 파트, 인원, 일정 순서를 유지한다. |
| 채팅 | 실시간 대화 레이아웃은 유지하고, 바깥의 전역 헤더·색 토큰·여백만 새 체계에 맞춘다. |

## 4. 첨부 모델과 업로드 흐름

### 4.1 선택한 방식: 임시 업로드 후 ID 연결

1. 클라이언트는 선택 즉시 파일 수, 확장자, 크기를 검사한다.
2. 통과 파일은 `multipart/form-data`로 업로드한다. 서버는 저장소에 저장하고, 현재 회원 소유의 임시 `FileMetadata`를 반환한다.
3. 게시글·공고 생성 또는 수정 요청은 파일 바이트가 아닌 `attachmentIds`만 보낸다.
4. 서버는 파일 소유자, 임시 상태, 허용 형식, 개수를 검증한 뒤 같은 트랜잭션에서 도메인 첨부 관계를 저장한다.
5. 작성 취소·실패로 연결되지 않은 임시 파일은 보존 기한 뒤 정리한다. 기존 `file_metadata` 행은 프로필·공연 포스터처럼 이미 사용 중인 파일이므로, 첨부 상태 도입 마이그레이션에서는 `ATTACHED`로 보존하고 새 업로드만 `TEMPORARY`로 생성한다.

선택 파일 중 하나가 실패해도 이미 성공한 파일과 본문을 보존할 수 있어, 파일별 재시도와 구체적 오류 표시가 가능하다.

피드는 텍스트만, 첨부만, 또는 둘을 함께 게시할 수 있다. 다만 `content`와 `attachmentIds`가 모두 비어 있으면 서버가 `INVALID_INPUT_VALUE`로 거절한다. 구인 공고는 기존처럼 제목과 모집 파트가 필수이며, 설명은 첨부와 독립적으로 선택 입력이다.

### 4.2 관계 모델

- `feed_post_attachment`: `post_id`, `file_metadata_id`, 표시 순서
- `recruitment_posting_attachment`: `recruitment_posting_id`, `file_metadata_id`, 표시 순서
- 두 관계는 별도 외래 키와 유니크 제약을 둔다. 범용 `targetType/targetId` 다형 테이블은 DB 참조 무결성과 삭제 규칙을 약화하므로 채택하지 않는다.
- `FileMetadata`에는 업로더와 임시/연결 상태, 원본 파일명, 실제 검증된 콘텐츠 타입, 크기, 저장 키를 관리한다.

### 4.3 파일 검증

- 허용 타입: `image/jpeg`, `image/png`, `image/webp`, `application/pdf`
- 한 게시글 최대 5개, 파일당 최대 10MB
- 프런트 확장자·크기 검사는 빠른 피드백일 뿐 신뢰 경계가 아니다.
- 서버는 멀티파트 전역 크기 제한과 함께 확장자, 선언 MIME, 파일 시그니처(JPEG/PNG/WebP/PDF)를 검사한다.
- 저장 키는 UUID 기반으로 생성하며, 원본 이름과 저장 경로를 분리한다.

## 5. API와 오류 계약

### 5.1 API 방향

| 동작 | 방향 |
| --- | --- |
| 임시 업로드 | `POST /api/files` multipart, 응답 `AttachmentResponse` |
| 임시 파일 삭제 | `DELETE /api/files/{fileId}`. 본인 소유 임시 파일만 허용 |
| 피드 작성·수정 | 기존 JSON body에 `attachmentIds` 추가 |
| 구인 등록·수정 | 기존 JSON body에 `attachmentIds` 추가 |
| 피드·구인 조회 | 응답에 `attachments[]` 추가 |

`AttachmentResponse`는 `id`, `originalName`, `contentType`, `size`, `url`, `kind(image|document)`를 제공한다. 목록 카드에는 대표 이미지 파생 정보만 제공해 불필요한 첨부 목록 전송을 피한다.

### 5.2 오류 응답

기존 공통 응답의 `error { resultCode, code, message }`를 유지하고, 선택적으로 `error.fields`를 추가한다. 기존 클라이언트는 `message`만 사용해도 동작하고, 새 작성 화면은 필드별 오류를 사용할 수 있다.

| 상황 | 코드 방향 | FE 표시 위치 |
| --- | --- | --- |
| 제목·내용·모집 파트 검증 실패 | `INVALID_INPUT_VALUE` + `fields` | 해당 입력 아래, 상단 요약 |
| 허용하지 않은 형식 | `INVALID_FILE_TYPE` | 실패 파일 행 |
| 파일당 크기 초과 | `FILE_TOO_LARGE` | 실패 파일 행 |
| 첨부 개수 초과 | `ATTACHMENT_LIMIT_EXCEEDED` | 첨부 영역 |
| 남의 파일 ID | `ATTACHMENT_NOT_OWNED` | 첨부 영역 |
| 이미 연결된 파일 | `ATTACHMENT_NOT_TEMPORARY` | 첨부 영역 |
| 임시 파일 만료·없음 | `FILE_NOT_FOUND` | 해당 파일 행 및 첨부 영역 |
| 저장소 I/O 실패 | `FILE_UPLOAD_FAILED` | 폼 상단, 실패 파일 행 |
| 네트워크 실패 | FE 전용 메시지 | 폼 상단, 재시도 행동 |

서버 로그에는 원인 예외를 남기되, 응답에는 저장 경로·인증 정보·내부 예외 메시지를 노출하지 않는다.

### 5.3 프런트 오류 UX

- 파일 선택 직후 실패한 행에는 이유, `다시 시도`, `제거`를 표시한다.
- 입력 오류는 해당 필드의 `aria-describedby`와 `aria-invalid`에 연결한다.
- 제출 실패 시 폼 상단의 `role=alert` 요약과 첫 오류 입력 포커스를 제공한다.
- 성공한 파일과 작성 중인 텍스트는 게시 요청 실패 후에도 유지한다.
- 브라우저 `alert()`는 사용하지 않는다. 문맥을 끊고 오류 대상을 가리지 못하기 때문이다.

## 6. 대안과 트레이드오프

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| 게시글 요청에 파일을 함께 전송 | 엔드포인트 수가 적다 | 파일별 재시도와 진행 상태가 약하고, 본문 검증 실패 시 업로드를 다시 해야 한다. |
| S3 사전 서명 URL 직접 업로드 | 대용량·CDN 확장에 유리하다 | 현재 로컬 저장소 운영과 초기 용량에 과하고, CORS·권한·정리 정책을 먼저 마련해야 한다. |
| 범용 다형 첨부 테이블 | 테이블 수가 적다 | 피드·구인 FK와 삭제 무결성을 DB가 보장하지 못한다. |
| `alert()` 중심 오류 | 구현이 짧다 | 파일·입력별 복구 행동을 안내하지 못하고 접근성이 낮다. |

## 7. 구현과 검증 순서

1. BE 첨부 엔티티·마이그레이션·저장소 검증·오류 응답 테스트를 작성한다.
2. 피드·구인 요청/응답/서비스/API에 첨부 ID 연결을 추가한다.
3. Next.js BFF 업로드·삭제 프록시와 API 타입을 추가한다.
4. 재사용 가능한 첨부 선택·업로드·미리보기 컴포넌트와 필드 오류 컴포넌트를 만든다.
5. 밝은 전역 레이아웃, 피드 작성 페이지, 피드·구인 목록/상세/작성 화면을 순서대로 개편한다.
6. BE 단위·통합 테스트, FE 단위 테스트, `typecheck`, `test`, `lint`, `check:colors`, `build`를 실행한다.
7. 로컬 브라우저에서 데스크톱·모바일의 업로드 성공/실패, 작성 실패 후 상태 보존, 목록·상세 표시를 확인한다.

## 8. 완료 판단

- 피드와 구인 공고에서 허용 파일을 업로드·연결·수정·삭제·조회할 수 있다.
- 형식, 크기, 개수, 소유권, 네트워크, 저장 실패가 원인과 위치에 맞게 표시된다.
- 기존 피드·구인 API의 첨부 없는 요청도 계속 동작한다.
- 전역 화면은 밝은 콘텐츠 중심 구조로 일관되고, 채팅의 실시간 기능은 회귀하지 않는다.
