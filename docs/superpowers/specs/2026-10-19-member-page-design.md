# 회원 페이지(사람 페이지) 설계

> **상태: 승인 (2026-10-19).** §7의 도메인 문서 변경을 반영했다. 구현은 아직 시작하지 않았다.

## 1. 목적

글·공연·공고에서 닉네임을 보고 "이 사람은 누구지?"라고 느꼈을 때, 그 사람의 프로필과 다른 활동으로 이어지게 한다.

2026-10-19 구조 파악에서 확인한 사실은 이렇다. 도메인은 깔끔하게 나뉘어 있지만 서로를 잇는 연결이 거의 없다. 특히 다른 회원을 보는 길이 백엔드부터 화면까지 하나도 없다. 이 설계는 그 연결 중 **사람을 중심으로 한 첫 번째 다리**다.

## 2. 확정한 결정 (2026-10-19 사용자 승인)

| # | 결정 | 이유 |
|---|---|---|
| 1 | **로그인한 회원만 볼 수 있다** | 공개 응답에 회원 식별자를 넣지 않는 고정 규칙(`DOMAIN-NOTICE-STATUTE.md` §6)을 바꾸지 않고 시작할 수 있다. 비로그인 공개 여부는 "로그인 벽 완화"와 함께 따로 정한다 |
| 2 | **모든 회원이 대상이고, MEMBER 도메인이 소유한다** | 어떤 닉네임을 눌러도 이어져야 한다. 인증 여부는 지금처럼 뱃지로 보여 준다 |
| 3 | **1단계에서는 프로필과 그 사람의 공연·글을 보여 준다** | 공고는 마감되면 의미가 줄어서 다음 단계로 미룬다 |

## 3. 사용자 흐름

```
글·댓글·공연 상세·공고·지원자 목록의 닉네임 클릭 (로그인 상태)
  ▼
/members/{회원번호}
  ├ 사진 · 닉네임 · 인증 뱃지 · 악기 · 자기소개
  ├ [메시지 보내기]           ← 본인이 아닐 때만
  ├ [내 프로필 편집]          ← 본인일 때만, /profile로 이동
  ├ 이 사람의 공연 (예정 공연 먼저)
  └ 이 사람의 글 (최신순, 더 불러오기)
```

- 로그인하지 않은 사람이 `/members/{id}`에 들어오면 기존 보호 경로처럼 로그인 화면으로 보낸다. 로그인 후에는 원래 페이지로 돌아온다(`proxy.ts`의 `next`).
- 비로그인 화면(홈 위젯, 공연 목록)은 공개 응답을 쓰기 때문에 회원 번호가 없다. 그래서 링크가 **생기지 않는다.** 따로 처리하지 않아도 결정 1과 맞는다.

## 4. 백엔드

DB 테이블 변경은 없다.

### 4.1 회원 페이지 조회 (MEMBER, 신규)

- `GET /api/members/{id}/profile` (인증 필수)
- 응답 `MemberPageResponse`: `{ id, nickname, verified, instruments[], bio, profileImageUrl }`
  - 내 프로필 응답(`ProfileResponse`)과는 **다른 클래스**를 쓴다. 넣기로 정한 필드만 들어간다.
  - 이메일·로그인 ID·가입일·동의 내역 같은 **식별·연락 정보는 절대 넣지 않는다.** 회원 검색(§3.2.1)과 같은 원칙이다.
  - 프로필을 아직 만들지 않은 회원은 빈 값으로 응답한다(404 아님). 내 프로필 조회와 같은 방식이다.
- 없는 회원과 **탈퇴한 회원은 똑같이** `MEMBER_NOT_FOUND`(404-03)로 응답한다.
  - 탈퇴 여부를 따로 알려 줄 이유가 없고, 탈퇴 회원의 익명 닉네임(`탈퇴한회원{id}`)을 페이지로 보여 줄 이유도 없다.
  - 탈퇴 회원이 남긴 글은 지금처럼 피드에 그대로 남는다(`Member.withdraw()` 주석의 원칙).
- 인증 뱃지는 기존처럼 `VerifiedPerformerService`로 파생한다.

### 4.2 작성자별 글 목록 (FEED, 기존 API 확장)

- 기존 타임라인 `GET /api/feed/posts?cursor=&size=`에 **선택 파라미터 `authorId`를 추가한다.**
  - 없으면 지금과 똑같이 전체 타임라인이다.
  - 있으면 그 회원의 글만, 같은 커서 규칙(id 내림차순, `size+1`)으로 준다.
- 새 API를 만들지 않고 파라미터를 더하는 이유: 응답 모양(`CursorPage<PostResponse>`)과 화면 부품(`useInfiniteList`)을 그대로 쓸 수 있다.

### 4.3 작성자별 공연 목록 (PERFORMANCE, 기존 API 확장)

- 기존 인증 목록 `GET /api/performances?scope=&page=&size=`에 **선택 파라미터 `organizerId`를 추가한다.**
  - `scope` 규칙(UPCOMING·PAST·ALL)은 그대로 적용한다.
- 공개 목록(`/api/public/performances`)에는 추가하지 않는다(결정 1).

### 4.4 인덱스

`feed_post.author_id`와 `performance.organizer_id`에는 인덱스가 없다. 지금 데이터 규모에서는 필요 없어서 1단계에서는 추가하지 않는다. "DB 변경 없음"을 지키기 위해서다. 데이터가 늘면 측정한 뒤 Flyway 마이그레이션으로 추가를 검토한다.

## 6. 화면

### 6.1 회원 페이지 `/members/[id]`

- `FE/proxy.ts`의 보호 경로에 `/members/:path*`를 추가한다.
- 화면 구성은 §3과 같다. 공연과 글 목록은 기존 카드(`PerformanceCard`, `PostCard`)를 다시 쓴다.
- 메시지 보내기는 기존 채팅방 만들기(`type: DIRECT, participantIds: [id]`)를 호출하고 `/chat/{roomId}`로 이동한다. 같은 상대와 만든 방이 있으면 백엔드가 그 방을 돌려준다(`ChatRoomService.createRoom`).
- 상태: 불러오는 중 / 없는 회원 / 정상. 기존 페이지와 같은 기준이다.
- 코드 배치: 데이터 요청·상태가 셋(프로필·공연·글)이라, 문서 규칙에 따라 `features/member-page/`로 분리할지 구현 시작 전에 정한다(`ARCHITECTURE-STATUTE.md` §1 Frontend).

### 6.2 닉네임 링크 (`AuthorBadge`)

- 받은 작성자 정보에 `id`가 있으면 `/members/{id}`로 가는 링크로 그린다. 없으면 지금처럼 글자만 보여 준다.
- 링크를 달지 않는 곳:
  - 채팅 상대 검색(`MemberSearchInput`): 누르면 "선택"이 되어야 하는 곳이다
  - 내 프로필 화면(`/profile`): 자기 자신이다
- 결과적으로 링크가 생기는 곳: 피드 목록·상세, 댓글, 공연 상세(로그인 시), 구인 목록·상세, 지원자 목록.

## 8. 테스트 (구현 시)

TDD로 진행한다. 테스트를 먼저 쓰고 구현한다.

- **BE 회원 페이지**: 정상 조회, 프로필 미생성 회원은 빈 값, 없는 회원·탈퇴 회원은 404-03, 비로그인은 401, 응답에 이메일·로그인 ID가 없는지 검사.
- **BE 글 목록**: `authorId`가 있을 때 그 회원 글만 나오는지, 커서 이어 붙이기, 삭제 글 제외, `authorId`가 없을 때 기존 결과가 그대로인지(회귀).
- **BE 공연 목록**: `organizerId`와 `scope`를 함께 쓸 때, 파라미터가 없을 때 기존 결과가 그대로인지(회귀).
- **FE**: `AuthorBadge`는 id가 있으면 링크, 없으면 글자. 회원 페이지는 본인·타인 버튼 분기, 404 상태. 메시지 보내기 후 채팅방 이동.
- 완료 기준: BE·FE 전체 테스트, 타입 검사, lint 통과. 실제 화면에서 데스크톱·모바일로 흐름을 확인한다.

## 9. 범위 밖

- 비로그인 공개 회원 페이지와 그에 필요한 공개용 주소값
- 그 사람의 구인 공고 목록(2단계 후보)
- 팔로우, 활동 통계, 인증 연주자 목록 페이지
- 작성자 인덱스 추가(§4.4)
- 공개 응답 규칙(`DOMAIN-NOTICE-STATUTE.md` §6) 변경
