# Attacca 에이전트 코딩 하네스

## 한 줄 요약

Attacca는 LLM 에이전트를 자유 생성기로 사용한 프로젝트가 아니라, 사람이 정한 제품 우선순위와 저장소 문서, 테스트·빌드·운영 검증 게이트 안에서 에이전트가 작은 단위로 구현하고 기록하는 방식으로 개발했다.

이 문서에서 말하는 **하네스 코딩(harness coding)**은 특정 제품이나 표준 프레임워크의 이름이 아니다. 이 프로젝트의 에이전트 작업을 일정한 품질 범위 안에 두기 위해 `AGENTS.md`, 아키텍처 문서, TODO 상태, 테스트, 배포 확인, 사람의 승인 절차를 함께 묶은 개발 운영 방식이다.

## 왜 하네스가 필요했는가

Attacca는 프론트엔드·백엔드·인프라·외부 인증·실시간 채팅이 함께 움직이는 개인 프로젝트다. 에이전트에게 기능 구현만 맡기면 다음 문제가 생길 수 있다.

- 이미 정한 도메인 경계와 API 계약을 모른 채 코드를 추가할 수 있다.
- 운영 환경의 시크릿, DNS, 보안 그룹을 코드 변경과 같은 방식으로 다룰 수 있다.
- 테스트가 통과해도 실제 브라우저·WebSocket·컨테이너 배포가 맞는지 알 수 없다.
- 같은 결정을 여러 번 논의하거나, 완료된 작업이 TODO에 남아 현재 상태를 흐릴 수 있다.

그래서 에이전트가 코드를 쓰는 능력보다 **무엇을 근거로 판단하고, 어디까지 실행하며, 무엇으로 결과를 증명하는지**를 먼저 고정했다.

## 작업 하네스의 구성

| 층 | 저장소의 장치 | 에이전트가 해야 하는 일 | 결과 증거 |
|---|---|---|---|
| 요구·우선순위 | 사용자 결정, `docs/TODO-*.md` | 이번 작업의 범위와 보류 항목을 구분한다 | TODO 상태, 사용자 확인 |
| 원칙·규칙 | `*-CONSTITUTION.md`, `*-STATUTE.md` | 기존 원칙과 API·도메인 규칙을 먼저 찾는다 | 설계 문서, 테스트 계약 |
| 작업 계획 | `docs/superpowers/plans/`, 필요 시 사양서 | 큰 변경을 작은 작업으로 나누고 의존 순서를 정한다 | 계획 문서, 작업 단위 |
| 구현 | `BE/`, `FE/`, `infra/`, `deploy/` | 현재 구조와 이름을 따르며 필요한 범위만 수정한다 | 코드 diff |
| 자동 검증 | Gradle/Vitest/TypeScript/ESLint/색상 검사/빌드 | 실패를 숨기지 않고 실패 원인을 고친다 | 테스트·검사 결과 |
| 운영 검증 | CI, GHCR, EC2 health, 브라우저 smoke | 운영 시크릿·DNS·배포·브라우저 동작은 사람이 승인한 범위에서 확인한다 | CI 결과, 컨테이너 상태, 화면·로그 |
| 기록 | `AI-ACTION-LOGS.md`, `AI-MAJOR-EVENT*.md`, `TODO-DONE.md`, TIL | 결정·트레이드오프·미검증 범위를 남긴다 | 재현 가능한 작업 기록 |

## 작업 흐름

### 1. 사람이 문제와 우선순위를 정한다

사용자는 제품 방향, 기능의 우선순위, 운영 비용과 위험에 대한 선택을 한다. 에이전트는 선택지를 비교하고 현재 코드와 문서를 근거로 구현안을 제시하지만, 다음 항목을 임의로 확정하지 않는다.

- RDS·S3·Blue/Green처럼 비용이나 운영 구조가 바뀌는 인프라 선택
- DNS·보안 그룹·OAuth 콘솔·운영 시크릿 변경
- 사용자에게 보이는 기능을 삭제하거나 도메인 규칙을 바꾸는 결정

결정되지 않은 항목은 구현하지 않고 백로그 또는 주요 사건 문서에 보류 이유를 남긴다.

### 2. 문서와 코드에서 작업 범위를 확인한다

작업 시작 전에 관련 문서와 실제 호출 경로를 확인한다. 전체 저장소를 무작정 읽는 대신 현재 작업에 필요한 문서만 찾고, 화면·API·도메인 규칙·BFF 계약·운영 배포 구조를 대조한다. 문서와 코드가 어긋나면 먼저 정합성을 복구하거나, 불일치 자체를 기록한 뒤 구현한다.

### 3. 테스트 또는 검증 기준을 먼저 만든다

작은 기능은 실패하는 테스트나 명확한 검증 기준을 먼저 만든다. 프로필 리팩터링에서는 기존 URL·요청 본문·응답 계약을 보존해야 한다는 기준을 API 테스트로 먼저 고정했다. 이후 기능 모듈을 구현하고, 라우트는 조합 역할만 담당하도록 줄였다.

### 4. 기능 경계 안에서 구현한다

에이전트는 한 번에 저장소 전체를 바꾸지 않는다. 기존 도메인과 기능 경계에 맞춰 변경하고, 공통화가 실제 중복을 줄일 때만 추출한다. 범위 밖의 개선점은 바로 섞지 않고 TODO나 후속 문서로 분리한다.

### 5. 여러 검증 게이트를 통과시킨다

단위 테스트만 통과한 것을 완료로 보지 않는다. 변경 위험에 따라 다음을 조합한다.

```text
targeted test
  -> full test
  -> typecheck / lint / color token check
  -> production build
  -> CI result
  -> deployed container health and revision
  -> browser/API/WebSocket smoke
```

실패한 검증은 결과를 감추지 않고 원인과 수정 내용을 기록한다. 색상 토큰 검사에서 `bg-black/75`가 하드코딩으로 잡혔을 때 `bg-scrim/75`로 교체하고 검사 결과를 다시 확인한 것이 한 사례다.

### 6. 운영 작업은 사람의 확인을 거친다

에이전트가 로컬 코드와 문서를 준비할 수는 있지만 운영 환경의 민감한 변경은 사용자가 직접 수행하거나 명시적으로 승인한다.

- EC2 `.env.prod`에 시크릿 입력
- 카카오 개발자 콘솔의 OAuth 설정
- AWS Security Group의 현재 SSH IP 변경
- DNS, Vercel 도메인, 운영 배포·롤백
- 브라우저에서 로그인·채팅·첨부 기능 확인

시크릿은 Git, Docker 이미지, CI 로그에 넣지 않는다. 운영에서 확인하지 못한 항목은 “완료”가 아니라 “미검증”으로 기록한다.

## Attacca에 적용한 사례

### BFF 합성으로 아키텍처 충돌 해결

홈 화면은 공연과 공지를 함께 보여줘야 했지만, 백엔드가 화면 전용 합성 로직을 갖지 않는다는 원칙과 충돌했다. 원칙을 몰래 약화시키지 않고 충돌을 문서화한 뒤, BE는 도메인별 범위 조회만 제공하고 화면 합성은 FE BFF에서 수행하는 방향으로 정리했다.

### staging 폐기 결정

`staging.attacca.site`가 별도 백엔드·DB·Redis를 바라보지 않고 운영과 같은 경로를 공유하는 상태를 확인했다. 사용자는 아직 사용자가 없고 개발 서버 비용을 줄이기로 결정했고, 에이전트는 Vercel·카카오·DNS·WebSocket origin에서 staging 참조를 순서대로 제거하고 공개 DNS·API·인증 채팅 smoke를 기록했다. 별도 격리 없는 staging을 개발 환경이라고 과장하지 않은 사례다.

### refresh session 보안 구조

브라우저에는 access token 쿠키만 남기고, refresh session은 opaque 값의 해시를 Redis에 TTL과 함께 보관하는 구조로 정리했다. 회전·grace period·로그아웃 폐기를 코드와 Redis TTL로 확인했으며, Redis에 저장된 실제 키와 운영 응답의 `Set-Cookie`를 사람이 직접 대조했다. 브라우저·컨테이너·Redis 세 지점의 증거를 연결한 사례다.

### 외부 공연 반입 기능의 폐기

KOPIS API의 응답 형식과 차단·파싱 실패를 운영에서 반복 확인한 뒤, 사용자는 이 기능을 제품 범위에서 제거하기로 결정했다. 에이전트는 키를 계속 요구하는 우회 구현을 추가하지 않고 관련 UI·환경변수·Compose 주입을 제거하고, 제거 후 BE health와 환경변수 부재를 검증했다.

### 프로필 기능 단위 리팩터링

`FE/app/profile/page.tsx`에 몰려 있던 API 호출·폼 상태·표현 컴포넌트를 `FE/features/profile/` 아래의 model, api, hooks, components로 분리했다. 기존 URL·요청·응답 계약은 바꾸지 않고 API 테스트를 먼저 작성했다. 결과는 FE 전체 99개 파일·587개 테스트 통과, typecheck·lint·색상 검사·production build 통과였다. 라우트는 조합자 역할을 유지하고 기능 코드는 기능 폴더에 두는 기준을 아키텍처 문서에도 반영했다.

### 첨부 미리보기와 CI 색상 검사

이미지 첨부는 MIME·파일 크기·파일 개수 검증을 유지하면서 게시글 안에서 미리보기로 확인할 수 있게 했고, PDF 등 문서는 파일 목록으로 구분했다. 운영에서 10MB 제한과 정상 이미지 게시·조회 smoke를 확인했다. 이후 CI 색상 검사에서 발견된 하드코딩 색상을 디자인 토큰으로 교체해 자동 게이트와 UI 작업을 연결했다.

## 사람과 에이전트의 책임

| 구분 | 에이전트 | 사람 |
|---|---|---|
| 제품 판단 | 선택지·영향·현재 코드 근거 정리 | 기능 도입·폐기·우선순위 결정 |
| 코드 | 테스트·구현·리팩터링·문서 초안 | 결과 검토와 범위 승인 |
| 운영 | 확인 명령·체크리스트·실패 해석 제공 | 시크릿 입력, 콘솔/DNS/AWS 변경, 최종 배포 승인 |
| 검증 | 자동 테스트·빌드·로그 분석 | 실제 계정으로 브라우저·OAuth·채팅·첨부 확인 |
| 기록 | TODO·액션 로그·주요 사건·TIL 갱신 | 결과 확인, 미검증 항목 승인 또는 보류 |

따라서 이 프로젝트의 정확한 표현은 “AI가 전부 개발했다”가 아니라 **문서와 검증 게이트를 갖춘 에이전트 보조 개발을 사람이 감독하고, 운영 위험이 있는 작업은 사람이 승인한 프로젝트**다.

## 포트폴리오에서 말할 수 있는 범위

### 말할 수 있는 것

- 저장소 규칙과 문서를 에이전트의 작업 입력으로 사용했다.
- TDD, 타입·린트·색상 검사·빌드·CI·운영 smoke를 단계별 증거로 연결했다.
- 코드 변경과 함께 결정 이유, 대안, 보류 조건, 트러블슈팅을 기록했다.
- 사용자 승인 없이 운영 시크릿·DNS·비용이 발생하는 인프라를 바꾸지 않았다.

### 아직 말하면 안 되는 것

- 단일 EC2에서 완전한 무중단 Blue/Green을 구현했다는 주장
- 대규모 트래픽이나 장애 상황에서의 성능·가용성 수치
- S3 백업과 RDS 전환이 운영 검증까지 끝났다는 주장
- 에이전트가 사람의 확인 없이 운영 환경을 자동 변경했다는 주장

현재도 단일 EC2의 SimpleBroker는 채팅 상태가 인스턴스 안에 있고, 업로드는 EC2 로컬 볼륨을 사용한다. 외부 STOMP relay·공유 presence, S3 운영 연동·백업 정책은 별도 검토 항목으로 남겨 두었다.

## 재현 가능한 검증 명령

프론트엔드 변경은 다음 게이트를 기본으로 사용한다.

```bash
cd FE
npm test -- --run
npm run typecheck
npm run lint
npm run check:colors
npm run build
```

운영 배포 뒤에는 CI 성공 여부, EC2 컨테이너의 `healthy` 상태, 이미지 revision, 핵심 화면의 브라우저 smoke를 별도로 확인한다. 어느 한 단계의 성공을 전체 배포 성공으로 대체하지 않는다.
