# 목이 감추는 프로토콜 제약 — "호출됐는가"만 검증하면 놓치는 것

## 무슨 일이 있었나

채팅 FE는 7태스크 TDD로 만들었고 테스트는 전부 초록이었다. 그런데 실제로 BE와 FE를 띄워 대화창을 열자 **실시간 수신이 하나도 동작하지 않았다.** 콘솔에는 이것만 떠 있었다.

```
Uncaught (in promise) There is no underlying STOMP connection
```

## 원인

대화창의 초기화 코드가 이랬다.

```ts
socket.connect({ onConnect: () => setConnected(true) });
unsub = socket.subscribeRoom(roomId, handler);   // ← 여기서 예외
```

`connect()`는 `client.activate()`를 부를 뿐이고, STOMP는 서버의 **CONNECTED 프레임이 도착한 뒤에야** 구독을 받는다. `@stomp/stompjs`는 그 전에 `subscribe()`를 부르면 예외를 던진다. 예외가 `init()` 프로미스를 깨뜨려 구독이 아예 걸리지 않았고, 결과적으로 상대 메시지도 자기 메시지도 화면에 오지 않았다.

전송은 멀쩡했다. 입력창이 `connected` 상태로 게이팅돼 있어 publish는 연결 이후에만 일어났기 때문이다. **BE 로그도 DB도 정상**이었다. 서버 쪽만 보면 아무 문제가 없어 보이는 유형의 결함이다.

## 왜 테스트가 못 잡았나

목이 이랬다.

```ts
const subscribe = vi.fn(() => ({ unsubscribe: vi.fn() }));
class MockClient {
  subscribe = subscribe;   // 언제 불러도 조용히 성공
}
```

이 목은 "`/topic/rooms/3`으로 구독을 요청했는가"는 검증하지만, **"언제 불러도 되는가"는 검증하지 않는다.** 그런데 STOMP에서 호출 시점은 부수적인 사항이 아니라 계약 그 자체다. 목이 실물보다 관대하면, 테스트는 실물에서 깨지는 코드를 통과시킨다.

## 고친 방법

먼저 목에 제약을 넣어 RED를 만들었다.

```ts
subscribe = (destination, cb) => {
  if (!this.connected) throw new Error('There is no underlying STOMP connection');
  return subscribe(destination, cb);
};
```

그리고 구독을 연결 이벤트에 종속시켰다. 구독 요청은 목록에 보관하고, 실제 STOMP 구독은 `onConnect`에서 건다.

```ts
onConnect: () => {
  // 재연결이면 이전 구독 핸들은 무효다. 초기화 후 다시 건다.
  rooms.forEach((room) => { room.sub = null; bind(room); });
  handlers?.onConnect?.();
},
```

덤으로 **재연결 문제도 같이 풀렸다.** STOMP는 재연결해도 서버측 구독을 복구해주지 않는다. 연결될 때마다 목록으로 다시 거는 구조라 끊겼다 붙어도 수신이 이어진다. 원래 코드는 이 경우에도 조용히 죽었을 것이다.

## 배운 것

* **목은 실물보다 관대해선 안 된다.** 실물이 던지는 조건에서 목도 던져야 한다. 관대한 목은 테스트를 통과시키는 게 아니라 결함을 숨긴다.
* **호출 여부가 아니라 호출 시점이 계약인 API가 있다.** 프로토콜 클라이언트(STOMP/WebSocket/DB 커넥션/트랜잭션)가 대체로 그렇다. 이런 API의 목은 상태 기계를 최소한이라도 흉내내야 한다.
* **"테스트 통과 = 완료"가 아니다.** 목으로 대체한 구간은 검증한 게 아니라 검증을 미룬 것이다. 실기동으로 확인하기 전까지는 미검증으로 적어두는 편이 정직하다.
* **증상이 "아무 일도 안 일어남"인 결함은 로그에 안 남는다.** 서버는 정상 응답하고, DB에는 데이터가 쌓이고, 화면만 조용하다. 이런 건 화면을 열어봐야만 보인다.
