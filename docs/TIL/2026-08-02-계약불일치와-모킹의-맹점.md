# 계약 불일치와 모킹의 맹점 (mocked green ≠ integration green)

> 작성일: 2026-08-02
> 카테고리: 테스트 / 프론트-백엔드 통합
> 태그: 계약테스트, 모킹, 직렬화, 통합버그

## 무슨 일이 있었나

피드(FEED) FE를 붙이면서, FE는 작성자 판정을 위해 게시글/댓글 응답의 `author.id`를 읽도록 짰다.
그런데 BE는 작성자 표시정보를 `record MemberDisplay(Long memberId, ...)`로 내보내고 있었고,
Jackson 기본 직렬화는 이를 `{"memberId": ...}`로 낸다. 즉 실제 응답에는 `author.id`가 **없다**.

결과:
- 런타임에 `post.author.id === undefined` → `canEdit(me, undefined)`는 항상 false
- **작성자 본인이 자기 글의 수정/삭제 버튼을 절대 볼 수 없다**(비-어드민은 삭제도 불가)

그런데 FE 단위 테스트(89개)도, BE 단위 테스트(310개)도 전부 초록불이었다.

## 왜 초록불이 이걸 못 잡았나

양쪽 테스트가 **각자 mock/fixture로 "같은 거짓 계약"에 합의**했기 때문이다.

- FE 페이지 테스트는 `author: { id: 5, ... }`를 손으로 만든 fixture로 렌더 → FE 코드와 fixture가 서로 `id`를 씀
- BE 컨트롤러 테스트는 `author.nickname`만 단언하고 `author.id`/`author.memberId`는 **아무도 단언하지 않음**

각 계층은 자기 세계 안에서 완결적으로 옳았다. 하지만 **실제 wire 형식**(BE가 정말 내보내는 JSON)을
검증하는 지점이 어디에도 없었다. 모킹은 "내가 기대하는 상대"를 만들어내므로,
상대의 실제 모습이 다르면 그 간극은 통합 지점에서만 드러난다. 단위 테스트 초록불의 합집합은
통합 초록불이 아니다.

## 어떻게 잡았고 어떻게 고쳤나

- **잡은 방법**: 태스크별 리뷰는 각자 계층만 봐서 못 잡았고, **전체-브랜치 리뷰**가 FE `author.id` 소비와
  BE `MemberDisplay` 직렬화를 나란히 놓고 대조해서 발견했다(교훈: 통합 리뷰는 계층 경계를 가로질러 봐야 한다).
- **고친 방법**:
  1. BE에서 `@JsonProperty("id")`로 wire 필드를 `id`로 맞춤(Java 접근자는 `memberId()` 유지, 호출부 무변경).
     FE·신원 엔드포인트(`MemberIdentityResponse.id`)·스펙과 전부 일관.
  2. **경계 계약 테스트 추가**: 컨트롤러 테스트에서 `$.data...author.id` 존재 + `author.memberId` 부재를 단언.
     이게 핵심 — 다시 깨지면 즉시 빨간불이 나도록 "실제 직렬화 필드명"을 못 박았다.

## 부수 교훈: 취약한 테스트 헬퍼

`@JsonProperty("id")` 추가가 Feed/Performance/Recruitment 컨트롤러 테스트 15건을 깨뜨렸다.
그 테스트들이 응답에서 리소스 id를 `json.replaceAll(".*\"id\":(\\d+).*", "$1")` **greedy** 정규식으로
뽑고 있었는데, 새로 생긴 중첩 `author.id` 때문에 greedy가 **마지막** id(작성자 것)를 집어버렸다.
`.*?`(non-greedy)로 바꿔 **첫** id(최상위 리소스 것)를 잡도록 수정.
DTO가 최상위 `id`를 항상 먼저 직렬화하므로 안전(레코드 컴포넌트 선언 순서 = 직렬화 순서).
→ 정규식으로 구조화된 응답을 파싱하는 건 취약하다. 필드가 하나 늘면 조용히 다른 걸 잡는다.

## 규칙으로 남길 것

1. **도메인 경계를 넘는 필드는 "실제 직렬화된 이름"을 테스트로 못 박는다**(모킹된 형태 말고).
   FE↔BE 공유 계약(응답 DTO 필드명)은 최소 한 곳에서 wire 형식을 단언한다.
2. 단위 테스트가 전부 통과해도 **계층을 가로지르는 리뷰**를 통합 관점에서 한 번 돌린다.
3. 구조화된 응답에서 값을 뽑을 땐 정규식보다 JSON 파싱을 쓴다. 굳이 정규식이면 non-greedy + 필드 추가 내성 고려.

## 관련

- 낙관적 UI 롤백은 스냅샷 복원 대신 **역연산 재적용**이 안전하다: `toggleLike`가 자기 역함수(involution)라
  실패 시 현재 상태에 다시 `toggleLike`를 적용하면, 그 사이 들어온 다른 토글을 덮어쓰지 않는다.
- React 훅에서 render 중 `ref.current` 변경은 `react-hooks/refs` 에러이고 `next build`를 실패시킨다.
  최신 값을 async 콜백에서 읽으려면 render가 아니라 **의존성 없는 `useEffect`**에서 ref를 동기화한다.
