# 어댑터로 훅 재사용 + 단일 파일 lint의 맹점

> 작성일: 2026-08-02
> 카테고리: 기타 (프론트엔드 설계 / 빌드)
> 태그: 재사용, 페이징, eslint, next-build

공연(PERFORMANCE) FE를 붙이며 얻은 두 가지 교훈.

---

## 1. 계약이 다른 API를 "어댑터"로 기존 훅에 재사용하기

피드는 **커서 페이징**(`{items, nextCursor}`), 공연 BE는 **오프셋 페이징**(Spring `Page`: `{content, number, last}`)이었다.
페이징 방식이 다르다고 무한스크롤 훅(`useInfiniteList`)을 새로 만들 필요는 없었다.

핵심은 **작은 순수 변환 함수 하나**로 두 계약을 잇는 것:

```ts
export function toCursorPage(page: SpringPage<Performance>): CursorPage<Performance> {
  return { items: page.content, nextCursor: page.last ? null : page.number + 1 };
}
```

- `cursor`를 "페이지 번호"로 재해석: 첫 로드 `cursor=null` → page 0, 이후 `nextCursor = last ? null : number+1`.
- `useInfiniteList`·`mergeCursorPage`(id 중복 제거)는 **한 줄도 안 바꾸고** 그대로 동작.
- scope 탭 전환은 리스트 컴포넌트를 `key={scope}`로 리마운트해 훅 상태를 리셋(훅에 별도 reset API 불필요).

교훈: 인터페이스가 다른 외부 계약을 만나면, 소비자(훅)를 고치기 전에 **경계에 얇은 어댑터**를 두면 기존 자산을 그대로 재사용할 수 있다. 어댑터는 순수 함수라 단위 테스트도 쉽다.

## 2. "단일 파일 eslint 통과" ≠ "빌드 통과"

등록 페이지 구현 시 `npx eslint app/performances/new/page.tsx`는 **에러 0**으로 통과했다.
그런데 나중에 `npx eslint .`(전체)에서 같은 파일이 **에러**로 잡혔다:

```
@next/next/no-html-link-for-pages
Do not use an `<a>` element to navigate to `/performances/`. Use `<Link />` instead.
```

내부 라우트로 가는 `<a href="/performances">`를 쓴 게 원인. `next build`는 eslint를 돌려 **에러에 실패**하므로 이건 빌드 브레이커였다.

왜 단일 파일 검사는 놓쳤나 → `no-html-link-for-pages`는 **프로젝트의 페이지/라우트 목록을 알아야** "이 href가 내부 라우트"인지 판정한다. 단일 파일만 lint하면 그 컨텍스트가 없어 규칙이 발현하지 않을 수 있다.

고침: `<a href="...">` → `<Link href="...">`(next/link). 외부 URL(`ticketUrl` 등)은 `<a target="_blank">` 그대로 OK.

교훈:
- 태스크 완료 게이트는 단일 파일 lint가 아니라 **`npm run build`(또는 `eslint .`)** 로 확인해야 한다. 특히 Next 프로젝트 규칙(`no-html-link-for-pages`, `no-img-element` 등)은 프로젝트 스코프에서만 정확히 뜬다.
- 내부 네비게이션은 항상 `<Link>`, 외부만 `<a>`.
